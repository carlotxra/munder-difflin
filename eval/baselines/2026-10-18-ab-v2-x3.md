## Reading the Copilot failures

Copilot often chains read-only git checks into one shell command (`git status && printf … &&
git show-ref …`). The eval's Copilot safe-mode allowlist doesn't cover all of those, so the
command is refused. Copilot then (correctly) stops instead of working around it. Those runs are
**eval artefacts**, not orchestration choices. The Denied column doesn't show them yet: the
Copilot parser does not read denials.

| Arm | Failures | Blocked by the eval allowlist | Real behaviour |
|---|---|---|---|
| Copilot V1 | 9 | G12#2; G9#2 and G9#3 partly | G1#2 (card left `todo`), G3#1 (invalid spawn request), **G5#1, G5#3** (decided a fee/account question itself), G10#3 (marked done with no review), G11#1 (approved merge not done) |
| Copilot V2 | 4 | G9#1, G11#1, G12#2 | G11#3: read hard rule 1 as "git is reserved to the harness" and did not merge an approved change |

## Conclusion

- **V2 meets the plan's bar:** a clear win on Copilot (G5 1/3 → 3/3; fewer real failures in
  G1, G3, G10 and G11) and no loss on Claude, at the same cost.
- **One V2 wording fix:** hard rule 1's exception ("landing approved work under rule 2") was
  read once as a ban. Say plainly that god runs the fast-forward himself, e.g. "you run
  `git merge --ff-only <reported SHA>` on the integration branch yourself".
- **Eval fix before trusting the landing numbers (G9, G11, G12) on Copilot:** widen the Copilot
  safe-mode allowlist to the read-only git commands it chains (`show-ref`, `rev-list`,
  `merge-base`, `printf`), and count its permission refusals in the Denied column.
